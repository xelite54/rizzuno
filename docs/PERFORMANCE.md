# Capacity evidence and limits

`REDIS_SERVER_BIN=<local redis-server> npm run test:load` starts two local realtime processes and one fresh Redis, progressing through 100, 500, 1000 authenticated synthetic clients. LOAD_LEVELS changes even concurrency values; LOAD_ALLOW_LARGE=1 permits up to 10000. Ramp is 100 sockets/s and the hard runtime cap is four minutes. It rejects external URLs/database credentials, so it cannot accidentally hit production. It uses fixture account/DB functions; real ticket signatures and gateway/coordinator/Redis paths are exercised. Output includes p50/p95/p99 and failures, with Postgres metrics explicitly null. A failing run is not evidence of capacity.

The harness measures sockets/authentication, search-to-match, skip/requeue, reconnect, dropped sockets, Redis ping, stream lag, queue depth, process CPU/RSS. It does not generate video traffic, measure TURN bandwidth or include real Google/SQL/provider costs. Run provider-backed staging acceptance before setting a launch limit. Use server telemetry for production Postgres latency, pool counts and waiting queries; load-fixture percentiles cannot stand in for those.

Vercel defaults to two pool connections per instance; Railway defaults to ten, both configurable up to 50. Budget total connections across peak serverless instances, persistent replicas and pooler limits. Use transaction-mode pooler for Vercel where appropriate; migrations use transaction-scoped state and query calls are not named prepared statements. Persistent Railway direct/session connections need an independent budget. Keep TLS verification and timeout limits.

Friend-message latest-page queries are bounded to 50 but older-history pagination remains an explicit product limitation. Posts are capped at 20. Inspect EXPLAIN (ANALYZE, BUFFERS) on representative staging data before new indexes or query rewrites; never drop an index because tiny production statistics show no use. The reply FK index supports referencing-row lookup. Private media delivery currently performs a DB reference check and authenticated storage fetch per request: benchmark that path and consider authorized caching/CDN only after a privacy review.

2026-09-19 local results are preserved in LOAD_TEST_RESULTS.json. The initial run failed due to O(n) online-count broadcasts on each arrival flooding streams. Coalescing to one broadcast per second and bounded burst buffering corrected that tested failure. Final 100/500/1000 runs authenticated every client, had zero reported match errors, exactly one intentional reconnect disconnection per level and successful reconnect. At 1000, search-to-match p95 was approximately 217 ms. This is synthetic gateway capacity evidence, not a production capacity certification.

The controlled public-launch gate is [STAGING_LOAD_PLAN.md](STAGING_LOAD_PLAN.md), including the guarded remote WS probe and the required real-media/TURN/provider matrix. The new per-action and heartbeat account/legal eligibility checks, retention locks and evidence snapshots must be included in staging database/pool measurements. No previous fixture result incorporates proof of those external costs.
