# Release controls

Required checks for `main`: `quality`, `security`, `realtime-integration`, `browser-webrtc` from `.github/workflows/ci.yml`. Quality runs npm ci, lint, root TypeScript, tests, and npm run build through an isolated compile-only environment. Browser tests use synthetic devices and no Google accounts; live credential tests are separate manual acceptance. Review failing audits rather than blindly running `npm audit fix --force`.

Enable a GitHub ruleset requiring pull requests, successful required checks, review, up-to-date branches (or merge queue), no force pushes, no branch deletion, and restricted bypass. Require checks for administrators too where practical. Enable secret scanning and push protection if available for the repository/plan. Gitleaks scans history in CI; organization repositories may need the action's license. Review/rotate any true-positive historical credential before rewriting history. These settings are documented, not claimed enabled.

Enable Railway's wait-for-CI/check suites setting (currently observed false) and equivalent protected Vercel deployment workflow. Direct main pushes must not auto-deploy unverified code. Do not run live credential acceptance on untrusted pull requests. Store deployment credentials only in protected environments with limited access.

Before deploy: provision IMAGE_STORAGE_URL/KEY/BUCKET (private), confirm TURN and web configuration, run all checks, check backups, review legal decisions, stage migrations, then deploy web/realtime compatibly. Next validates web config on Vercel build and runtime registration. Railway's built-in RAILWAY_SERVICE_ID selects realtime validation so OAuth/storage secrets are not required on a realtime-only service. Percent-encoded DB passwords remain encoded through URL parsing; TLS verification is always enabled remotely. Set DATABASE_SSL_CA_REQUIRED=true for endpoints requiring the supplied CA.

Do not deploy CI's `.next` output: it contains placeholder public endpoints. Always rebuild in the target environment with real production configuration. The checked-in workflow builds only to prove compilation.

Legal versions are release-coupled: deploy Vercel and Railway from the same Git revision, including `lib/legalVersions.ts`. Both the web acceptance writer/checker and the realtime hello check use `lib/db.ts` and its shared `REQUIRED_DOCUMENTS`; there is no separate Railway version override. Current versions are age18 `2`, Terms `2026-09-24`, and Privacy `2026-09-24`. After a legal-version change, confirm both deployed revisions before testing acceptance → ticket → WebSocket ready. A mismatched deployment cannot be repaired by refreshing tickets: deploy the matching revision, then have the user accept the current documents. Never backdate acceptance or relax the server gate to hide release drift.


Release must be a normal reviewed merge or revert, never a force-push workflow. Configure deployment providers to accept only the exact main commit whose four required checks succeeded. A passing previous commit or PR head does not authorize a different merge revision. Restrict manual deploy/promote tokens and environment bypass; record release SHA, check-run URLs, operator launch review reference and rollback SHA. These external settings are requirements, not asserted to be enabled by this edit.

Run `npm run launch:check` with actual deployment values before release. Production config validation invokes the same gate on both web and realtime. Do not copy `scripts/ci-launch-fixture.mjs` declarations or CI `.next` output into production. Apply/stage migration 0015 with the server owner and re-run database privilege verification. Public rollout is blocked until the regional checklist, safety coverage, retention scheduler and provider-backed staging evidence are complete.

Browser CI explicitly provisions Chrome and dependencies and logs its version/path. Test processes use isolated profiles and poll `DevToolsActivePort` plus the local CDP version endpoint; failures include bounded browser stderr. The existing 15-second startup deadline and media assertions remain. Only disposable GitHub Linux fixture browsers use `--no-sandbox`/`--disable-dev-shm-usage` to avoid runner user-namespace and shared-memory restrictions. This exception never applies to application browsers or non-fixture production probes.
